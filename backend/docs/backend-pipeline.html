01 / The complete process

Three parts of the story lifecycle

  1. Prepare the story

    Fetch RSS entries. Select articles. Write and translate drafts. Run checks.

  2. Approve and publish

    Save the draft for editors. Complete the required approvals. Release approved text.

  3. Maintain the story

    Deliver a reader’s feed. Collect feedback. Correct, review, or expire the story.

02 / Start a run

A scheduled task starts the newsroom

30 min

Default interval between scheduled runs.

An editor can also start a run manually.

  • The scheduled task skips a new run if another run is active.
  • The default limit is four stories per run.
  • The system selects Oulu, or the first active geographic community.
  • Runs left active for more than two hours can be marked as failed.

Defaults can change through settings. agents/tasks.pyagents/services.pyconfig/settings.py

03 / Wire desk

The system reads Kaleva’s RSS feed

Input

One fixed feed contains Kaleva’s free articles.

The system processes up to 25 entries per run.

Each entry supplies a title, text, article address, and sometimes an image address.

Processing

The system removes HTML from the title and text.

If the entry has no image, the system checks the article page for an image address.

The draft uses the RSS text. This stage does not extract the full article text from the web page.

newsroom/wire.py: fetch_entries(), page_image()

04 / Store and filter

Only eligible articles reach selection

Store source records

  • A content hash identifies the title and text.
  • Unchanged content does not create another record.
  • Changed content at the same address creates a new source version.

Select candidates

  • Check up to 120 records fetched within the last 48 hours.
  • Keep records that have no linked snippet.
  • Exclude opinion and commercial content with text rules.

If the RSS request fails, recent stored articles can still enter the run.

newsroom/wire.py: store(), content_type(), run_wire_desk()

05 / News editor

Relevance and member votes select articles

Jev criterionWeight
Connection to the local area30%
Effect on readers30%
Information readers can act on15%
Importance as news25%

Jev receives the article and a summary of the community’s readers.

The system adds member vote strength to the relevance score. It adjusts vote strength by reader group.

If Jev fails or has no key, fixed rules score local relevance, age, and interests.

newsroom/news_editor.py: audience(), combine(), community_votes(), rank()

06 / Reporter and explainer

AI writes a Finnish draft and reader context

Reporter

The model writes a headline, a short summary, and key facts.

The instructions permit only facts from the supplied source.

If the model fails, the system uses the source title and first sentences. This fallback requires review.

Explainer

The model explains the effect on newcomers, seasonal workers, students, and residents.

If this step fails, the draft continues without these explanations.

The system passes each selected story through these desks in sequence.

newsroom/desks.py: reporter(), explainer()newsroom/runner.py: story_graph()

07 / Translator

Each community supplies its language targets

  • The system combines community languages with members’ preferred languages.
  • The model translates the headline, summary, key facts, and reader explanations.
  • The system rejects text that fails its language checks or remains too similar to Finnish.
  • Missing translations create a note. Readers can later receive an approved fallback version.

Sámi text requires a human translator. The AI translator skips Sámi languages.

newsroom/runner.py: target_languages(), _translate()newsroom/desks.py: translate_one()

08 / Fact checker and standards editor

Rules identify numbers and editorial risks

Number checks

The system compares numbers in the Finnish draft with the source text.

Unsupported numbers can require review. Missing numbers in translations create warnings.

These checks do not verify every claim against independent sources.

Editorial checks

The system checks for high-risk and sensitive topics.

Examples include health, legal matters, crime, and minors.

Detected issues can require an editor’s checklist confirmation. Sensational headlines can receive a warning.

newsroom/desks.py: fact_checker(), standards()editorial/checklist.py

09 / Copy desk

The system saves a draft for editors

Ready to send

No collected issue blocks the story.

An editor can use the ready-story send action.

Needs review

At least one issue requires review. The queue shows the reasons.

Stored output

  • Snippet and language versions
  • Source link, topics, and risk tier
  • Check results and review tasks
  • Expiry date and any review date

Both results start in pending review. The automatic desks do not publish the story.

newsroom/copy_desk.py: verdict(), file_story()

10 / Human approval

Two approval paths reach publication

Regular review queue

An editor approves the story.

Language reviewers approve translated versions separately.

The Finnish version and whole-story checks must pass before publication.

Ready-story send action

A person chooses to send a ready story.

The action approves open review tasks and all available non-Sámi versions in one step.

The system records that person as the approver.

The ready-story path uses batch approval. It does not require a separate reviewer action for each non-Sámi translation.

agents/services.py: send_story()editorial/services.py: approve(), can_publish(), publish()

11 / Community vote desk

Unused articles become future coverage choices

10

Top unselected articles form the normal new shortlist.

Existing articles with votes can stay longer while they remain eligible.

  • The system updates the shortlist after story processing.
  • Members vote for articles they want the newsroom to cover.
  • The next run adds these votes to article scores.
  • The system marks selected candidates as covered and drops stale candidates.

“Covered” records selection for processing. It does not prove that an editor published the story. newsroom/shortlist.py: publish()

After publication

The story enters
a continuing cycle

The API selects an approved language version. Readers receive ranked stories. Their feedback can change future coverage or return a story to review.

Publication releases a story to the feed. It does not end the editorial process.

12 / Feed delivery

The API selects visible text for each reader

Story eligibility

  • The story must have published status.
  • Its expiry date must not have passed.
  • It must have an approved version in the reader’s language chain.

Language order

  1. Reader’s preferred language
  2. English, if available and approved
  3. Finnish, if available and approved

GET /api/feed/snippets/ returns the feed. An explicit language parameter can override the profile language. feed/services.py: language_chain(), published_snippets()

13 / Reader ranking

Feed ranking orders published stories

Base ranking signalWeight
Reader interests40%
Location and community25%
Recent reader activity20%
Time since publication15%

The API normally ranks a window of up to 200 recent eligible stories.

Activity uses views, completed reads, expansions, and likes from the last seven days.

If enabled, Jev adjusts the top selection for a signed-in reader.

Article selection happens before drafting. Feed ranking happens when the reader requests published stories.

15 / Community notes

Reader agreement can add public context

A helpful note requires

  • At least three ratings
  • A mean helpfulness score of at least 0.70
  • Positive ratings from at least two reader situation groups

Members can propose context on a post or a news story.

Authors cannot rate their own note. Helpful notes can appear with the story.

The background translation task currently handles helpful notes on community posts.

A helpful note does not itself approve or rewrite a news story.

notes/services.py: status_from_ratings(), rate()notes/tasks.py: translate_note()feed/services.py: published_snippets()

16 / Reports and corrections

A report returns a story to review

  1. The reader reports a problem

    The system stores the report and changes the story status to reopened. The normal feed excludes it.

  2. An editor reviews the story

    The system creates review tasks at top priority. Edits to a previously published story create a correction record.

  3. The editor completes approval

    Publication checks must pass again. Publication releases pending correction records.

The current report path reopens a story immediately. It has no report-count threshold. feed/services.py: report()editorial/services.py: reopen(), _apply_edits(), publish()

17 / Review dates and expiry

Time limits control story availability

Risk tierExpiry after draft creation
Low3 days
Medium7 days
High14 days

High-risk drafts also receive a review date three days after creation.

A scheduled task runs every 15 minutes.

It marks published stories as expired after their expiry date.

It creates a refresh review task when the review date passes.

A refresh task alone leaves the story published. The feed separately excludes stories past their expiry date.

18 / The next cycle

Feedback returns through specific paths

Active connections

  • Coverage votes affect the next article selection.
  • Reader activity affects later feed ranking.
  • A changed RSS article can create a new source version and enter selection again.
  • Editors can link reader questions to an answering story.

Current limits

Three repeated matching questions can flag a story candidate.

The automatic notification or agent trigger for that candidate remains a TODO.

A new source version follows the candidate path. It does not automatically replace the old published snippet.

communities/services.py: record_question(), answer_post()newsroom/wire.py: store(), run_wire_desk()

19 / Operations and failure handling

The backend records progress at each desk

Recorded evidence

AgentRun stores run status and the current desk.

RunStory stores each selected article’s stage and any error.

AgentStep stores desk output and processing time.

Editorial logs record approvals, edits, and publication events.

Failure behaviour

An invalid AI JSON response gets one retry. Failed calls return a reason to the desk.

A failed story does not stop the remaining selected stories.

A run can finish successfully while its result reports failed stories.

Check story counts and review reasons as well as the run status.
